# Heuresis + Codex Loop 使用说明

本文说明如何从 ResearchStudio 产出的完整 idea 和代码原型出发，配置 `controller_bash`，并一键启动 `Heuresis -> Codex -> trial -> evidence -> next Heuresis` 闭环。

每个新 case 必须先定义统一任务契约。完整字段、proposal/result schema 和校验命令见 [`TASK_CONTRACT.md`](TASK_CONTRACT.md)。

## 1. 目录约定

控制层通过配置服务任意 case。任务名称和目录结构不属于 controller 协议，例如：

```text
<case_dir>/
  human_ideas/                   # 人类原始 idea 和任务要求
  machine_ideas/                 # ResearchStudio 生成的 idea card / phase0-phase4 产物
  implementation/               # Codex 生成并由后续轮次修改的代码原型
  datasets/                      # 当前任务的数据

controller_bash/
  config.env                     # 通用入口；要求选择当前 case 配置
  configs/                       # case 配置与通用模板
  .env                           # 可选本地覆盖，不建议放密钥
  run_loop.sh                    # 一键闭环入口
  run_round.sh                   # 单轮：收集上下文、Heuresis、Codex、静态检查
  scripts/run_trials.py          # trial 执行器：skip/local/rjob/simulated
  scripts/execution_backends.py  # 统一 rjob：同步、提交、轮询、日志、超时
  state/                         # 每轮上下文、建议、trial 结果、ledger
```

任务专属内容只能放在 case 配置、case 上下文和 case 实现中，不应写入 controller 的 Python、prompt 或 schema。启动时用 `CONTROLLER_CONFIG` 选择配置。密钥不应写入 case 配置；Heuresis/Boyue 的 API 信息继续放在 `HEURESIS_ENV_FILE` 指向的 Heuresis `.env` 中。

## 2. 最小启动命令

如果目标是验证已迁移任务，而不是启动新一轮搜索，使用同一个回归入口：

```bash
run_research --task tasks/cifar/task_spec.yaml
run_research --task tasks/vcc25/task_spec.yaml
```

入口同时位于仓库根目录和 `~/.local/bin/run_research`。如果当前 shell 尚未把用户命令
目录加入 PATH，可先执行 `export PATH="$HOME/.local/bin:$PATH"`，或在仓库根目录使用
`./run_research`。

上述命令默认是 `rjob_dry_run`。真实运行使用
`--execution-mode rjob`。CIFAR 的 BADE/AFR 和 VCC25 的 CRPM/pseudo-bulk 都由各自
Task Adapter 编译，后续同步、提交、轮询、日志和标准结果解析使用同一个 controller。

工程调试优先用模拟模式，不占 GPU：

```bash
LOOP_START_ROUND=0 LOOP_MAX_ROUNDS=3 \
RUN_CODEX_APPLY=1 HEURESIS_SUGGESTION_MODE=real \
TRIAL_EXECUTION_MODE=simulated MAX_TRIALS_PER_ROUND=1 \
bash controller_bash/run_loop.sh 3
```

确认要真实跑 GPU trial 时再切换为 rjob：

```bash
LOOP_START_ROUND=0 LOOP_MAX_ROUNDS=3 \
RUN_CODEX_APPLY=1 HEURESIS_SUGGESTION_MODE=real \
TRIAL_EXECUTION_MODE=rjob MAX_TRIALS_PER_ROUND=1 \
RJOB_GPU_PER_TRIAL=1 RJOB_TIMEOUT_MIN=60 \
bash controller_bash/run_loop.sh 3
```

追加运行时，`run_loop.sh` 的参数是“最大轮次上界”，不是新增轮数。例如已有 `round_0` 到 `round_5`，要追加 3 轮：

```bash
LOOP_START_ROUND=6 LOOP_MAX_ROUNDS=9 bash controller_bash/run_loop.sh 9
```

## 3. 主路径参数

这些参数定义项目、Heuresis、Codex 和输出位置。

| 参数 | 作用 | 如何配置 |
|---|---|---|
| `ROOT_DIR` | 总工作区根目录 | 设为包含 ResearchStudio、Heuresis、controller 和各 case 的根目录 |
| `PROJECT_ROOT` | 当前 case 根目录 | 例如 `/.../<case_dir>` |
| `TASK_SPEC` | 当前 case 的统一任务契约 | 必须指向经过校验的 `task_spec.yaml` |
| `IMPLEMENTATION_DIR` | 代码原型目录 | 当前 case 的实现目录，例如 `/.../<case_dir>/implementation` |
| `CONTROLLER_DIR` | 控制层目录 | 通常为 `/.../controller_bash` |
| `HEURESIS_DIR` | Heuresis 仓库目录 | 例如 `/.../Heuresis_PJLAB-boyue` |
| `PYTHON` | Heuresis 使用的 Python | 建议指向 Heuresis 虚拟环境：`$HEURESIS_DIR/.venv/bin/python` |
| `CODEX_BIN` | Codex CLI | 当前为 `/root/.local/bin/codex` |
| `HEURESIS_ENV_FILE` | Heuresis API `.env` | 放 Boyue/OpenAI 兼容 API 的 URL、token、model |

## 4. ResearchStudio 上下文参数

这些参数告诉 Heuresis 本轮要读哪些 idea、报告、代码、历史结果。

| 参数 | 作用 | 配置建议 |
|---|---|---|
| `CONTEXT_TEXT_FILES` | 文本上下文，冒号分隔 | 放 `ambiguous_idea.md`、ResearchStudio idea card、实现 README、历史 reports |
| `CONTEXT_JSON_FILES` | JSON 上下文，冒号分隔 | 放 ResearchStudio `method_view.json`、`phase4_implementability.json`、历史 trial/summary/ledger |
| `CONTEXT_CODE_GLOBS` | 代码上下文 glob | 通常为 `$IMPLEMENTATION_DIR/**/*.py` |
| `CONTEXT_MAX_CHARS_PER_FILE` | 单文件截断长度 | 默认 `30000`；上下文太大时可调小 |

典型配置：

```bash
CONTEXT_TEXT_FILES=/.../<case_dir>/human_ideas/idea.md:/.../<case_dir>/machine_ideas/idea.detail.en.md:/.../<case_dir>/implementation/README.md:/.../<case_dir>/implementation/reports/*.md
CONTEXT_JSON_FILES=/.../<case_dir>/machine_ideas/method_view.json:/.../<case_dir>/machine_ideas/phase4_implementability.json:/.../<case_dir>/state/evidence_ledger.json:/.../<case_dir>/state/round_*/trial_results.json
CONTEXT_CODE_GLOBS=/.../<case_dir>/implementation/**/*.py
```

## 5. Loop 状态参数

| 参数 | 作用 | 配置建议 |
|---|---|---|
| `LOOP_START_ROUND` | 从第几轮开始 | 新 case 从 `0`；追加运行填下一个 round |
| `LOOP_MAX_ROUNDS` | 最大轮次上界 | 跑 `0,1,2` 三轮时填 `3` |
| `ROUND_PREFIX` | round 目录前缀 | 默认 `round`，生成 `round_0` |
| `STATE_DIR` | 控制状态目录 | 默认 `controller_bash/state` |
| `REPORT_DIR` | 汇总报告目录 | 建议放在实现目录 `reports` 下 |
| `ARTIFACT_DIR` | trial 输出目录 | 建议放在实现目录 `artifacts` 下 |
| `EVIDENCE_LEDGER` | 全局证据账本 | 默认 `controller_bash/state/evidence_ledger.json` |
| `CONTINUE_ON_TRIAL_FAILURE` | trial 失败是否继续下一轮 | 工程调试建议 `1` |
| `MAX_TRIALS_PER_ROUND` | 每轮最多执行几个 trial | 调试建议 `1`，避免一次提交过多任务 |
| `MAX_CODE_CHANGES_PER_ROUND` | 给 Heuresis 的代码变更预算提示 | 当前主要是提示参数 |

## 6. Heuresis 参数

| 参数 | 作用 | 配置建议 |
|---|---|---|
| `HEURESIS_SUGGESTION_MODE` | 建议生成模式 | `real` 调 Boyue/API；`mock` 只生成假建议 |
| `HEURESIS_SUGGESTION_TEMPERATURE` | LLM 温度 | 默认 `0.25`，偏稳 |
| `HEURESIS_SUGGESTION_TIMEOUT_SEC` | Heuresis API 超时 | 默认 `180` |
| `HEURESIS_SUGGESTION_MAX_RETRIES` | API 重试次数 | 默认 `2` |
| `HEURESIS_SUGGESTION_JSON_RETRIES` | JSON 解码失败重试次数 | 默认 `2` |
| `HEURESIS_DATASET_TOOL_MAX_CALLS` | 每轮 proposal 前允许的 Dataset Adapter 工具调用次数 | 默认 `4`；仅开放白名单结构化动作 |
| `SUGGESTION_SCHEMA` | Heuresis proposal schema | 使用 `schemas/proposal_v2.schema.json` |

Heuresis 输出会写到：

```text
controller_bash/state/round_N/heuresis_suggestion.json
controller_bash/state/round_N/heuresis_suggestion.dataset_tool_trace.json
```

当任务绑定 `dataset_ref` 时，Heuresis 可以在输出最终 proposal 前调用
`dataset_adapter` 的 `describe`、`inspect`、`list_splits`、`capabilities`、
`validate`、`prepare` 或 `resolve`。controller 会限制读取条数、阻止切换到未绑定
数据集、移除物理路径，并把每次请求和返回写入 trace。Heuresis 仍不能直接生成
数据路径、shell 或 rjob 命令。

## 7. Codex 参数

| 参数 | 作用 | 配置建议 |
|---|---|---|
| `RUN_CODEX_APPLY` | 是否让 Codex 按 Heuresis 建议改代码 | 调试 loop 时设 `1`；只看建议时设 `0` |
| `CODEX_APPLY_MODE` | Codex 模式 | `real` 真运行；`mock` 只写占位日志 |
| `CODEX_MODEL` | Codex 模型 | 空值使用默认 |
| `CODEX_SANDBOX` | Codex 沙盒 | 默认 `workspace-write` |
| `CODEX_ALLOWED_DIR` | Codex 允许编辑目录 | 必须指向 `IMPLEMENTATION_DIR` |
| `RUN_STATIC_CHECK` | Codex 后是否静态检查 | 建议 `1` |
| `STATIC_CHECK_COMMAND` | 自定义静态检查命令 | 留空则用默认 `py_compile` |

注意：Codex 应运行在控制/开发节点，不应放到 GPU rjob 节点运行。Codex prompt 已明确：不要在 CPU/control 节点运行导入 `torch` 或训练模型的 runtime/unit/smoke 测试；这些验证交给 `rjob` 或 `simulated` trial。

## 8. Trial 执行模式

`TRIAL_EXECUTION_MODE` 决定 Heuresis 生成的 `sweep_trials` 如何执行。

| 模式 | 行为 | 适用场景 |
|---|---|---|
| `skip` | 不执行，只写 skipped | 配置检查 |
| `dry_run` | 同 `skip` | 配置检查 |
| `simulated` | 只生成调度链路凭据，不产生科研指标 | 工程闭环调试 |
| `local` | 在本地运行 trial command | 仅适合不依赖 GPU/torch 的命令 |
| `rjob_dry_run` | 生成 rjob 提交命令但不提交 | 检查 rjob 参数 |
| `rjob` | 真提交 rjob | 真实 GPU 实验 |

推荐流程：

1. `simulated` 跑通 Heuresis/Codex/ledger 闭环；其 `primary_metric` 固定为空，不可当实验结果。
2. `rjob_dry_run` 检查 H 集群参数。
3. `rjob` 小 smoke，每轮 `MAX_TRIALS_PER_ROUND=1`。
4. 确认可训练后，再放大 trial 数量或训练时长。

## 9. rjob/GPU 参数

| 参数 | 作用 | 配置建议 |
|---|---|---|
| `RJOB_NAMESPACE` | H 集群 namespace | 当前 `ailab-deepdivegzy` |
| `RJOB_CHARGED_GROUP` | 计费/配额组 | 当前 `deepdivegzy_gpu` |
| `RJOB_IMAGE` | rjob 容器镜像 | 需包含 torch/CUDA/项目依赖 |
| `RJOB_GPU_LIMIT` | 控制层允许单 trial 最大 GPU | 默认 `2` |
| `RJOB_GPU_PER_TRIAL` | 每个 trial 请求 GPU 数 | 调试建议 `1` |
| `RJOB_CPU` | CPU 核数 | 当前 `20` |
| `RJOB_MEMORY` | 内存 MB | 当前 `20000` |
| `RJOB_MOUNT` | GPFS 挂载 | 必须让 rjob 能访问代码和数据 |
| `RJOB_PRIVATE_MACHINE` | H 集群机器策略 | 当前 `group` |
| `RJOB_HOST_NETWORK` | 是否 host network | 当前 `false` |
| `RJOB_TAIL_LINES` | 拉取日志尾行数 | 默认 `500` |
| `RJOB_LOG_RETRIES` | 拉日志重试次数 | 默认 `3` |
| `RJOB_LOG_RETRY_INTERVAL_SEC` | 拉日志重试间隔 | 默认 `10` |
| `RJOB_POLL_INTERVAL_SEC` | 轮询间隔 | 建议 `60`，避免高频轮询 |
| `RJOB_TIMEOUT_MIN` | 单 trial 等待超时 | smoke 可 `30-60`，长训练需更大 |
| `RJOB_SYNC_SOURCE` | 控制节点代码根目录 | 通常设为 OMNI-AR 根目录 |
| `RJOB_SYNC_PATHS` | 要同步的相对路径，冒号分隔 | 只包含 `tasks`、`controller_bash` 和当前 case |
| `RJOB_SHARED_FOLDER` | rjob package 的共享盘目录 | 必须位于可访问的共享存储中 |
| `RJOB_SYNC_EXCLUDES` | rsync 排除项，冒号分隔 | 排除 `.git`、虚拟环境和缓存 |
| `RJOB_CANCEL_ON_TIMEOUT` | 超时后是否取消任务 | 默认 `1`，并保存取消日志 |

GPU 节点通常无外网。不要把 Codex/API 调用放到 rjob worker 里；rjob 只负责跑训练命令。任务代码也不得手写 `rjob submit/get/logs/delete`，这些操作统一由 execution backend 完成。

## 10. 常用启动配方

只生成 Heuresis 建议，不改代码、不跑 trial：

```bash
RUN_CODEX_APPLY=0 RUN_TRIALS=0 \
HEURESIS_SUGGESTION_MODE=real \
bash controller_bash/run_loop.sh 1
```

真实 Heuresis + Codex，trial 用模拟结果：

```bash
LOOP_START_ROUND=0 LOOP_MAX_ROUNDS=3 \
RUN_CODEX_APPLY=1 HEURESIS_SUGGESTION_MODE=real \
TRIAL_EXECUTION_MODE=simulated MAX_TRIALS_PER_ROUND=1 \
bash controller_bash/run_loop.sh 3
```

真实 Heuresis + Codex + 1-GPU rjob smoke：

```bash
LOOP_START_ROUND=0 LOOP_MAX_ROUNDS=3 \
RUN_CODEX_APPLY=1 HEURESIS_SUGGESTION_MODE=real \
TRIAL_EXECUTION_MODE=rjob MAX_TRIALS_PER_ROUND=1 \
RJOB_GPU_PER_TRIAL=1 RJOB_TIMEOUT_MIN=60 \
bash controller_bash/run_loop.sh 3
```

rjob 参数 dry-run：

```bash
LOOP_START_ROUND=0 LOOP_MAX_ROUNDS=1 \
RUN_CODEX_APPLY=0 TRIAL_EXECUTION_MODE=rjob_dry_run \
MAX_TRIALS_PER_ROUND=1 \
bash controller_bash/run_loop.sh 1
```

## 11. 输出怎么看

每轮主要产物：

| 文件 | 内容 |
|---|---|
| `state/round_N/context.json` | 给 Heuresis 的完整上下文 |
| `state/round_N/heuresis_suggestion.json` | Heuresis 建议、消融计划、Codex 任务、trial 命令 |
| `state/round_N/validation.json` | schema 校验结果 |
| `state/round_N/codex_apply.log` | Codex 应用日志 |
| `state/round_N/trial_results.json` | trial 执行记录 |
| `state/round_N/round_summary.json` | 机器可读轮次摘要 |
| `<case_dir>/implementation/reports/heuresis_codex_round_N.md` | 人类可读轮次摘要 |
| `state/evidence_ledger.json` | 全局轮次索引 |

## 12. 关键注意事项

- `simulated` 只用于工程调试，不是科学实验结果。
- `rjob` 才是真实训练结果；真实训练前确认 `RJOB_IMAGE` 内有 torch/CUDA 和所需依赖。
- 每轮先限制 `MAX_TRIALS_PER_ROUND=1`，确认稳定后再增加。
- 代码路径、数据路径尽量用绝对路径；历史失败主要来自 rjob 工作目录变化导致相对 `datasets` 找不到。
- 正常超时会由 controller 自动取消并记录；如果直接杀死 controller 进程，已提交的 rjob 仍可能继续运行，需要人工检查。
- `controller_bash/.env` 可以做本地覆盖，但不要放长期密钥；密钥放 Heuresis 的 `.env`。
