## Autonomous Model Selection at L5

Implemented autonomous model selection for the KnowledgeDrivenVcc25Worker's L5 layer.
Previously, L5 only saw a single model candidate (KnowledgeStore ranking + truncation),
so the decision agent had no opportunity to compare methods.

### Changes

1. **L5 JSON schema** (`hier_loop/schemas/layer_decision.L5.schema.json`):
   Added `selected_model_id`, `selected_repository_id`, `selection_reason`, and
   `rejected_alternatives` as required fields in `coding_request`.

2. **RecordingDecisionBackend** (`hier_loop/layer_agent.py`):
   - Added `_extract_candidates()` to parse model/repo card IDs from injected knowledge
   - Added `_build_l5_coding_request()` to populate selection fields from actual
     knowledge content instead of hardcoding lingshu-vcc-85m
   - Selected model = first-ranked model from knowledge; rejected = remaining models

3. **build_layer_prompt** (`hier_loop/layer_agent.py`):
   - Added `_extract_candidate_profiles()` to parse structured per-model comparison
     data (readiness, adapter_id, compatibility, evidence) from rendered knowledge
   - L5 prompts now include `candidate_profiles` array and updated instruction
     telling the agent to compare and select

4. **Tests** (`tests/hier_loop/test_knowledge_worker.py`,
   `tests/domain_knowledge/test_lingshu_skill.py`):
   - Fixed `test_l5_model_skill_returns_repository_and_model_execution_facts`
     (was expecting only 1 model, now expects >=2 with lingshu present)
   - Added 6 new tests: prompt contains candidate_profiles, decision populates
     selected_model_id and rejected_alternatives, selected model is highest-ranked,
     schema requires selection fields, validate rejects missing fields, execution
     worker receives selected_model_id

All 46 related tests pass.

## Multi-Signal Ranking & Expanded L5 Candidate Space

Improved KnowledgeStore.query() ranking and L5 skill candidate injection.

### KnowledgeStore new ranking algorithm

Sort key (ascending tuple, 6 levels):
```
(layer_rank, weighted_overlap, readiness_order, -smoke_evidence, compatibility_rank, card.id)
```

| Level | Signal | What it captures |
|---|---|---|
| 1 | layer_rank (0/1) | Card's layers includes query layer |
| 2 | weighted_overlap | title=3, tags=2, summary=1 |
| 3 | readiness_order | ready=0 ... reference_only=4 |
| 4 | -smoke_evidence | count of passed smoke (excluding infrastructure_probe) |
| 5 | compatibility_rank | direct_task_candidate=0 ... reference_only=6 |
| 6 | card.id | stable sort only |

The previous algorithm used alphabetical card.id as primary tiebreaker.
Now it only fires when all other signals are equal.

### What compatibility.level means

7-level enum on model cards, ranked from most to least task-aligned:
direct_task_candidate (0) > existing_internal_route (1) > finetune_candidate (2)
> trainable_candidate (3) > future_finetune_candidate (4) > future_train_candidate (5)
> reference_only (6).

Determined by:
1. Whether H1 checkpoint or runnable code exists
2. Whether adapter / output conversion must be written from scratch
3. Length and severity of `gaps` list
4. Smoke evidence state

Distinct from execution_readiness (which describes asset/code/weight
readiness in isolation) — compatibility describes how ready it is for
THIS task.

### Changes

1. **KnowledgeStore ranking** (`domain_knowledge/store.py`):
   - Replaced flat token-overlap count with weighted overlap (title=3, tags=2, summary=1)
   - Added `_smoke_evidence_score()`: counts passing smoke evidence entries
   - Added `_compatibility_rank()`: maps vcc25_compatibility.level to ordinal
   - New sort key: `(layer_rank, weighted_overlap, readiness_order, -smoke_evidence, compatibility_rank, card.id)`
   - `card.id` is now the final tiebreaker only, not a primary signal

2. **L5 skill** (`skills/vcc25/lingshu.py`):
   - Query all L5-eligible models (max_results=50) instead of hard-capping at 3
   - Raised L5 default token budget from 1200 to 2400
   - Interleave model+repository pairs so models render before budget is exhausted

3. **Tests**:
   - Added 4 ranking tests (non-alphabetical ordering, smoke evidence effect,
     lingshu always first, >=4 candidates with default budget)
   - Added 2 worker tests (rejected_alternatives >=3, candidate_profiles >=4)

Result: L5 agent now sees 6 model candidates (up from 3) with improved
ranking that reflects evidence and compatibility rather than alphabetical accident.
All 52 tests pass.



## Architecture Q&A: KnowledgeDrivenVcc25Worker vs Vcc25Worker

Reviewed the two-worker relationship against `hier_loop/{knowledge_worker,vcc25_worker,cli,loop,knowledge_bridge,layer_agent}.py`.

- `KnowledgeDrivenVcc25Worker` is NOT a peer of `Vcc25Worker`. It is a *wrapper*:
  - owns `KnowledgeBridge` (inject) + `LayerDecisionBackend` (decide) + optional `execution_worker: Vcc25Worker`.
  - L1..L4: handled in-place by `KnowledgeDrivenVcc25Worker.step()` (planning only, no GPU).
  - L5: delegates to `execution_worker.step()` (`Vcc25Worker`) — only L5 path goes to the execution engine.
- `Vcc25Worker` standalone (`--worker vcc25`) handles all L1..L5 itself (L1..L4 plan-quality proxy, L5 real/mock/rollout trial).
- `--worker knowledge_vcc25` wires `KnowledgeDrivenVcc25Worker(KnowledgeBridge, HistoricalDecisionBackend(memory), execution_worker=Vcc25Worker(config, memory))` and passes that to `HierarchicalLoop`.
- `HierarchicalLoop.run()` iterates `for round -> for layer in loop_range -> for step in 1..max_steps: worker.step(layer, round, step, ctx)`. Exit per layer via `evaluate_exit`. After each layer: emit `transfer` (adjacent next-in-range) + any `direct_whitelist` direct edges. Experience cards are `rollup_cards`-ed into `context["experience_cards"]`; per-layer capacity signal → `internalise_signals`.
- Memory is injected by `HierarchicalLoop._inject_memory()` (not by KnowledgeBridge): adds `memory_block`/`memory_used`/`memory_fingerprint` to step context; `KnowledgeDrivenVcc25Worker` and `Vcc25Worker` only *read* these.
- `KnowledgeBridge` selects exactly one `ResearchSkill` per layer (`can_activate`), returns a `KnowledgeInjection` with `card_ids` + sha256 `content_hash` + `token_budget`; raises `KnowledgePreflightError` on mismatch.
- `HistoricalDecisionBackend` overrides L5 decision: picks an executable `candidate_variant` from `memory_manager.real_candidates("L5")` filtered by `VALID_VARIANTS`; raises if all variants failed.
- `Vcc25Worker._pick()` is memory-aware: exploits best real outcome, else explores an untried frozen seed; falls back to default schedule.
- `Vcc25Worker` modes: `mock` (no engine, deterministic score), `offline` (deterministic), `rollout` (planning+reasoning only, writes decisions), `real` (subprocess to `official_h1_adapter`, writes validation record, calls `_memorize_live`).

Common diagram errors to call out (cross-checked against code):
1. Treating the two workers as sequential peers — actually wrapper/inner.
2. Drawing knowledge injection as hitting L5 directly — actually `KnowledgeBridge.inject()` runs for every layer L1..L5 inside `KnowledgeDrivenVcc25Worker.step()`.
3. Showing "Agent" as a separate runtime from `KnowledgeDrivenVcc25Worker` — actually `KnowledgeDrivenVcc25Worker` *is* the agent orchestrator; `LayerDecisionBackend.decide()` is the only "LLM/agent" call and its only inputs are knowledge + prior decisions + prompt (no fabricated scores).
4. Putting Memory on the `Vcc25Worker` side only — `HierarchicalLoop._inject_memory()` injects the memory block into context for *all* layers; `Vcc25Worker` only consumes `memory_used`/`memory_hits` and (L5) calls `memory_manager.remember_live()` + `real_candidates()`.
5. Showing experience-card flow only at the end of a round — cards are emitted *per layer exit* (`_route_experience`) and `rollup_cards` is applied into context after each layer, so the next adjacent layer already sees rolled-up cards.
6. Drawing `direct_whitelist` as the default path — default route is *adjacent next-in-range*; direct edges are optional cross-layer shortcuts that may even target layers outside `loop_range`.
7. Treating `L5` as the only layer that produces a real score — true only in `real` mode; in `mock`/`offline`/`rollout` modes L5 also returns a deterministic proxy score, and L1..L4 always return plan-quality proxies.
8. Showing a single "Agent" box for all five layers — each layer has its own decision type (`direction`/`problem`/`hypothesis`/`mechanism`/`coding_request`) and the prompt + validation schema differ per layer.
