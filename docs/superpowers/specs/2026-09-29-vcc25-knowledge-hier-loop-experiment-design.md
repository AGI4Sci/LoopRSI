# VCC25 Knowledge-Driven Hierarchical Agent Experiment Design

## 1. Goal

Build an isolated experimental path that lets the existing five-layer research loop use the VCC25 knowledge base to propose, implement, and validate changes to a Lingshu-based candidate. The experiment succeeds only if a frozen candidate obtains a canonical final VCC25 `pearson_delta` greater than `0.306` without using final-test expression data during search.

This work does not replace the knowledge store, ResearchSkill classes, model adapters, or the existing remote RSI checkout. It connects the already implemented knowledge interfaces to an executable research loop in a separate workspace.

## 2. Verified Starting State

- `domain_knowledge/store.py` loads and queries the approved VCC25 cards.
- `skills/vcc25/lingshu.py` returns layer-specific fragments for L1 through L5.
- `adapters/vcc25/` validates declared model and repository assets without executing arbitrary code.
- `tasks/vcc25/task_plugin.yaml` declares the three Lingshu ResearchSkill entry points.
- The current `hier_loop.Vcc25Worker` does not load those skills. L1 through L4 produce fixed text, while L5 selects from a fixed variant/seed list.
- Rollout/offline scores generated by `Vcc25Worker` are synthetic and are not scientific evidence.
- The remote RSI checkout declares `skills/vcc25` but does not contain that directory.
- `controller_bash/scripts/apply_skill_context.py` expects the older `skill.manifest.skill_id` interface and is incompatible with the new `ResearchSkill.skill_id` interface.
- The repository contains a coding-agent execution path that works in an isolated candidate workspace.
- `official_h1_autonomous_research_loop.py` performs train/validation-only candidate selection and explicitly does not read test expression data or claim an official score.
- The existing canonical `run_trial` path generates and evaluates official-test predictions, so it must not be used inside the search loop.

All generated code, prompts, logs, metrics, patches, and predictions must live in a newly created experiment workspace. The workspace may refer to large immutable datasets and model weights by absolute path; it must not copy or modify them.

The experiment has two evaluation authorities:

1. `search_validation`: train and validation data only; repeatable and eligible for Agent reward.
2. `final_official`: the single frozen candidate selected at the end of validation search; it may run once for the entire experiment and is never eligible for search reward or memory ranking.

Every result record must include its authority. A missing or unknown authority makes the result ineligible for promotion.

## 4. Architecture

### 4.1 Knowledge bridge

A small bridge loads the task plugin, activates the ResearchSkill appropriate to the current layer, and adds the returned `PromptFragment` to the loop context. It records the skill ID, card IDs, content hash, and token budget so the run can prove which knowledge influenced each decision.

The bridge accepts both the new `ResearchSkill.skill_id` property and legacy manifest-backed skills. Compatibility is implemented in the isolated experiment copy rather than the remote source checkout.

### 4.2 Knowledge-driven worker

An experimental worker replaces fixed L1-L4 text with structured decisions:

- L1 chooses a research direction from paper evidence.
- L2 states a concrete prediction problem and comparison target.
- L3 proposes a falsifiable hypothesis.
- L4 selects a mechanism and describes why it should affect validation PCC.
- L5 turns the approved hypothesis into a bounded coding-agent request.

Each layer consumes the previous layer's structured output plus its own knowledge fragment. Invalid output, missing provenance, or restricted identifiers fail the step instead of silently falling back to a historical candidate.

### 4.3 Isolated code generation

L5 invokes the existing coding-agent runner against a disposable candidate workspace. The prompt permits edits only in candidate implementation paths and requires an explicit hypothesis, patch summary, training command, validation command, and expected artifacts. The original remote RSI and Lingshu directories remain untouched.

The first experiment permits one candidate and one repair attempt. This keeps the initial cost bounded and makes failures diagnosable before increasing the search budget.

### 4.4 Validation executor

The search executor uses the validation-only autonomous research entry point. It must enforce all of the following before execution:

- train, validation, and test target lists are disjoint;
- no final-test expression path is supplied to the candidate process;
- candidate outputs remain inside the experiment workspace;
- the command and environment are archived before execution;
- the validation result includes seed, data counts, code hash, runtime, and metric provenance.

The initial small-data smoke run is operational evidence only. It cannot promote a candidate. Promotion requires a full validation run under a fixed seed set and a comparison against a Lingshu baseline evaluated through the same validation contract.

### 4.5 Reward and memory

Only full `search_validation` results produce a reward:

```text
reward = candidate_validation_pcc - same_contract_lingshu_validation_pcc
```

Synthetic rollout scores, plan-quality scores, smoke metrics, historical final-test scores, and `final_official` results are excluded from reward and memory ranking.

The loop stores the hypothesis, retrieved card IDs, patch hash, validation score, delta, runtime, and failure reason. Later rounds may retrieve these records as experience, but knowledge cards and experiment experience remain separate data types.

## 5. Execution Phases

### Phase A: no-GPU integration proof

Create the isolated workspace, stage the required local knowledge modules, load the three ResearchSkills, and run the five layers without candidate execution. The proof passes when every layer records a non-empty knowledge fragment and L5 produces a schema-valid coding request.

### Phase B: small-data smoke

Run one generated candidate on a bounded train/validation subset. Confirm code activation, artifact generation, split isolation, and metric collection. The score is labeled `smoke_only` and cannot be compared with `0.306`.

### Phase C: full validation search

Establish the same-contract Lingshu validation baseline, then run the promoted candidate on the full validation protocol using the frozen seed set. Return the validation delta to the five-layer loop. Additional rounds are allowed only after the preceding round has complete evidence.

### Phase D: frozen final evaluation

Freeze the best candidate by content hash, generate official predictions once, and run canonical VCC25 evaluation. The project goal is met only if canonical `pearson_delta > 0.306`. Failure to exceed the threshold remains a valid experiment result and must not be rewritten as success.

## 6. Artifacts and Auditability

Each run produces:

- `run_manifest.json`: source revisions, knowledge revision, environment, phase, and evaluation authority;
- `layer_decisions.jsonl`: L1-L5 structured decisions and knowledge provenance;
- `candidate_request.json`: bounded L5 coding request;
- `candidate.patch` and `candidate_code_sha256.json`;
- `split_audit.json`;
- `validation_result.json` or `final_result.json`;
- stdout/stderr logs with secrets redacted;
- `summary.json` with promotion eligibility and failure reasons.

Artifacts are append-only after a run finishes. A new attempt receives a new run ID rather than overwriting prior evidence.

## 7. Failure Handling

- Missing knowledge cards: stop before L5.
- Skill interface mismatch: fail preflight; never continue without provenance.
- Coding-agent failure: preserve its logs and allow at most one repair attempt.
- Split audit failure or test-expression access: terminate the run and mark it ineligible.
- GPU timeout or out-of-memory: record the resource failure; do not fabricate a score.
- Incomplete validation metrics: do not calculate reward.
- Final score at or below `0.306`: report the measured result and end this experiment. The result must not be fed back into candidate selection, and this experiment may not submit a second final-test evaluation.

## 8. Testing

Local tests must cover:

- L1-L5 skill activation and provenance;
- new and legacy skill-ID compatibility;
- rejection of missing/unknown evaluation authority;
- exclusion of smoke, synthetic, and final-test results from reward;
- generation of an L5 coding request without executing it;
- enforcement of candidate workspace boundaries;
- serialization of all audit artifacts.

The remote preflight repeats these checks in the isolated workspace before any GPU job is submitted.

## 9. Non-Goals for the First Experiment

- Training the decision model itself;
- supporting STATE or PerturBench execution in the first live loop;
- broad hyperparameter search;
- changing the canonical VCC25 evaluator;
- modifying either remote source checkout;
- treating a simulated, smoke, or validation score as proof of exceeding `0.306`.
